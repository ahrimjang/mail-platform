# 사내 알림 SaaS 포크 설계 — 이메일 파이프라인을 다채널로

> 착수 전 계획만 정리한 문서. 이메일(Outpace)과는 **별개의 사내용 제품**으로,
> 이 저장소를 포크해 시작하는 걸 전제로 한다. "포트 하나 추가하면 끝"이 아니라
> 실제로는 성격이 다른 다섯 층의 일이 섞여 있어서, 그 층을 나눠 적어둔다.
>
> **왜 지금이 아닌가**: Outpace 자체가 아직 매출 전이다(목표 2026-09). 스코프를
> 넓히면 이메일 하나도 완결 못 지을 위험이 있다 — 착수는 Outpace 매출 궤도에
> 오른 뒤로 미루는 걸 권한다. 이 문서는 "그때 가서 헤매지 않기 위한" 사전 정리다.

## 배경

기존 서비스(Outpace)와 별개로, 사내에서 이메일·SMS·카카오 알림톡·웹푸시를
아우르는 알림 SaaS를 새로 만든다. 맨땅에서 짜지 않고 이 저장소를 포크하는
이유는 단순하다 — **큐 기반 비동기 처리, 테넌트별 동시성 제어, 속도 제한, DLQ,
복구 스위퍼가 전부 채널과 무관한 문제라 이미 검증된 걸 다시 만들 이유가 없다.**

다만 "이메일 파이프라인에 다른 기능만 붙이면 된다"는 기대는 절반만 맞다.
아래 다섯 층 중 ①만 진짜 "붙이기"고, 나머지 넷은 각각 리팩터링·신규 설계·
외부 협의·스코프 축소로 성격이 다르다.

## 다섯 층

### ① 그대로 재사용 — 손 안 대는 부분

채널과 무관한 인프라 문제라, 포크해서 그대로 가져가면 된다.

| 재사용 대상 | 왜 그대로 되는가 |
| --- | --- |
| 큐 기반 비동기 처리 (적재 후 즉시 반환, 워커가 드레인) | 채널이 뭐든 "쪽지 1장 큐에 넣고 워커가 처리"는 동일 |
| 조건부 UPDATE claim 패턴 전부 | 발송·팬아웃·완료판정·A/B — 전부 채널과 무관한 동시성 문제 |
| 테넌트별 토큰버킷 속도 제한 | 카카오·SMS도 업체별 초당 발송 한도가 있음 — 오히려 여기서 더 중요해짐 |
| DLQ·복구 스위퍼 | 그대로 |
| 이벤트 스트림(Kafka) 기반 오픈·클릭 추적 | 웹푸시도 클릭 추적 개념은 동일 |
| 헥사고날 모듈 경계(core/infra/api/worker) | 포트·어댑터 구조 자체를 그대로 유지 |

### ② 도메인 모델 채널 중립화 — 리팩터링

지금 도메인 모델이 이메일 어휘로 굳어 있다.

```java
Campaign { subject, body(HTML), unsubToken, trackingToken }
MailMessage { recipient, unsubToken, trackingToken }
```

- `subject` — SMS·웹푸시엔 없거나 의미가 다름(웹푸시는 title+body+아이콘)
- `body(HTML)` — SMS는 90바이트 텍스트(초과 시 LMS 자동 전환), 카카오는 사전 승인된
  템플릿 변수만 채우는 방식
- `unsubToken` — 카카오는 옵트아웃 방식 자체가 다름(채널 차단은 카카오톡 안에서 발생)

**할 일**: `channel` 필드를 추가하는 정도로 끝날 수도, `content`를 채널별 하위
타입으로 나눠야 할 수도 있다. 착수 전에 SMS·카카오·웹푸시 각각의 발송 API 스펙을
먼저 훑고 나서 모델을 확정한다 — 반대로 하면 스키마를 두 번 갈아엎는다.

### ③ 채널별 수신자 모델 신규 설계 — 새로 짜야 함

"수신자"의 정체가 채널마다 다르다.

| 채널 | 수신자 식별자 | 생명주기 |
| --- | --- | --- |
| 이메일 | 이메일 주소 | 고정값. 바뀌지 않음 |
| SMS | 전화번호 | 고정값 |
| 카카오 알림톡 | 카카오 채널 친구 여부 | 친구 추가·차단에 따라 변함. 사전 승인된 템플릿만 발송 가능 |
| 웹푸시 | 브라우저별 구독 엔드포인트 + 암호화 키(VAPID) | **기기·브라우저마다 별도 구독**. 만료·갱신됨 |

특히 웹푸시는 "구독"의 생명주기가 이메일의 "연락처 등록"과 근본적으로 다르다.
한 사람이 데스크톱·모바일에서 각각 구독하면 별도 레코드가 되고, 브라우저 데이터를
지우면 그 구독은 조용히 죽는다. 지금의 `contacts`/`list_memberships` 모델을
그대로 못 쓰고, 채널별 수신자 테이블을 새로 설계해야 한다.

### ④ 외부 업체 심사 — 개발 밖의 병목

개발 일정과 무관하게 며칠~몇 주가 걸리는 항목이라, **가장 먼저 신청부터
넣어야 한다.**

| 채널 | 필요한 절차 | 비고 |
| --- | --- | --- |
| 카카오 알림톡 | 비즈메시지 채널 심사 통과 + 템플릿 사전 승인 | 개발 다 해놔도 심사 끝나기 전엔 못 보냄 |
| SMS | 발신번호 사전등록(통신사 심사) | |
| 웹푸시 | VAPID 키 발급(즉시) + **HTTPS 필수** | 사내 인트라넷이 HTTP면 웹푸시 자체가 동작 안 함 — 인프라팀 확인 선행 |

### ⑤ 사내용으로 축소·재정의 — 스코프 걷어내기

외부 SaaS(Outpace) 전용 코드는 사내 도구에 필요 없다. 포크 직후 걷어내는 게
나중에 안 쓰는 코드를 끌고 다니는 것보다 낫다.

| 걷어낼 것 | 이유 |
| --- | --- |
| 랜딩페이지·요금제·베타 가입 정원 | 외부 고객 유치용 |
| 공개 구독 API(`X-Api-Key`) | 외부 고객 대상 기능 |
| 월 발송량 과금·플랜 한도(`PlanLimits`, `usage_snapshots`) | 사내는 과금이 아니라 부서별 사용량 집계 정도로 축소 |
| 구글 로그인 | 사내 SSO(있다면)로 교체가 자연스러움 |
| `AGENTS.md`의 "outpacemail.com 실운영" 등 서비스 설명 | 그대로 두면 새 프로젝트 설명이 거짓말이 된다 — **문서는 처음부터 새로 쓴다** |

**워크스페이스 개념도 재정의가 필요하다.** 지금은 "가입 = 워크스페이스"(외부
고객 자기등록) 방식인데, 사내라면 "관리자가 부서/팀 단위로 만들어주는" 방식이
맞다. 가입 이메일 인증·베타 정원 같은 게이트도 사내에선 의미가 없어진다.

## 포크 전에 정리할 것 (원본 파이프라인)

포크하는 순간부터 **버그도 복사된다.** 지금 고치면 한 번, 포크 후에 발견하면 Outpace 와
새 SaaS 두 곳을 각각 고쳐야 한다. 목록과 우선순위는
[REVIEW-product.md 8절](REVIEW-product.md)에 있고, 포크 관점에서 중요한 건 이 세 갈래다.

| 갈래 | 왜 포크 전인가 |
| --- | --- |
| 🔴 정확성·안전 버그 | 두 번 고치는 비용도 문제지만, 발송 사고는 채널이 늘수록 표면적이 커진다 |
| 🔴 본문 검증 | 채널별 검증(SMS 90바이트·카카오 템플릿 변수)이 붙을 자리가 지금 비어 있다 |
| 🔵 참여 카운터 핫 로우 | 이메일만으로도 대형 캠페인에서 병목. 채널이 늘면 같은 카운터에 트래픽이 몇 배 |

*2026-09-23 기준 완료*: `</body>` 앞 삽입, 워커 종료 대기 시간, 운영자 시더 대소문자.

**발신 도메인 인증은 반대로 포크 이후가 낫다** — SMS 발신번호·카카오 채널도 같은 성격의
"발신처 인증" 문제라, 지금 이메일 전용으로 짜면 나중에 다시 만든다.

- [ ] `AGENTS.md`·`README` 새로 작성 — 새 제품의 목적·도메인·배포 방식 기준으로
- [ ] `.env`·`certs/` 등 실제 시크릿이 딸려오지 않았는지 확인(원본 저장소도 커밋 금지 대상)

      이후 Outpace 쪽 마이그레이션과 번호가 겹치거나 자동으로 합쳐지지 않는다
- [ ] 랜딩·요금제·구독 API·플랜 과금 등 ⑤에서 걷어낼 것부터 먼저 정리 후 채널 확장 착수

## 권장 착수 순서

1. **④ 외부 업체 심사 신청** — 개발과 무관하게 지금 넣어도 됨, 병목이 가장 김
2. **⑤ 사내용 스코프 정리** — 걷어낼 것 걷어내고 워크스페이스 모델부터 재정의
3. **② 도메인 모델 설계** — 채널별 스펙(③에서 조사한 것)을 먼저 훑고 확정
4. **③ 채널별 수신자 모델 구현**
5. **① 채널 어댑터 연결** — 여기서야 비로소 "포트 하나 추가"가 실제로 마지막 단계가 된다

①을 가장 마지막에 두는 이유: 지금 "포트만 붙이면 된다"는 기대의 함정이
①을 맨 처음으로 여기는 데서 온다. 실제로는 ②~④가 먼저 정리돼야 ①이 진짜
"붙이기"로 끝난다.
