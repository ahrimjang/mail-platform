# 대용량 트래픽 점검 — 2026-09-14

> 기준 커밋 `9866ae1`. "이 시스템이 대용량 트래픽을 감당하는가"를 코드·설정·측정 기록으로
> 확인한 결과다. 착수는 나중에 한다 — 여기서는 현재 상태와 위험의 순서만 정해 둔다.
> 할 일 목록은 [ROADMAP-scale.md](ROADMAP-scale.md), 과거 측정 원본은
> [loadtest/RESULTS.md](../loadtest/RESULTS.md), 병목 해결 경위는 [RETRO-scaling.md](RETRO-scaling.md).

## 요약

- 발송 파이프라인은 대용량을 전제로 설계됐고, 병목 두 개(동기 팬아웃, 메시지당 DB 왕복)는
  측정 → 수정 → 재측정으로 해결한 기록이 있다.
- **지금 운영의 실제 상한은 코드가 아니라 외부 계약과 인프라다.** SES 일일 할당량 50,000통을
  모든 테넌트가 나눠 쓰고, 모든 구성요소가 4GB 서버 한 대에 한 벌씩만 있다.
- 측정은 개발 PC 한 대에서만 했다. 운영 노드에서 잰 적이 없고, 끝까지 드레인을 잰 최대
  규모는 5,000명이다. 2026-09 하드닝(claim 토큰 종료, 억제 팬아웃 필터 등) 이후 재측정도 없다.
- 베타 규모(정원 10곳, 일 5만 통)에는 여유가 크다. 규모가 커지면 **SES 할당량 → 서버 메모리 →
  발송 기록 테이블 증가 → 메시지당 DB 왕복** 순으로 막힐 가능성이 높다.

## 1. 적용된 확장 기술

| 기술 | 위치 | 효과 |
|---|---|---|
| 비동기 파이프라인 | `CampaignService.create` → 팬아웃 잡 1건 발행 | 리스트 크기와 무관하게 등록 응답이 상수 시간 |
| keyset 스트리밍 팬아웃 | `CampaignFanoutService.expand` (1,000명 페이지, OFFSET 없음) | 100만 명도 메모리 일정, 재개 커서로 중간 재시작 가능 |
| 원자적 조건부 UPDATE claim | 발송·팬아웃·예약 릴리스·A/B 승자·완료 판정 | 워커 N대에서도 중복 발송 0, 분산 락 불필요 |
| 리스너 동시성 | 워커 `concurrency 8` / `max-concurrency 16` / `prefetch 10` | 워커 1대 처리량 7.7배 |
| 테넌트별 속도 제한 | `JdbcSendRateLimiter` (Postgres 토큰버킷) + `mail.send.throttled` TTL 1초 파킹 큐 | noisy neighbor 해소, 새 인프라 없음 |
| 실패 격리·복구 | DLX → `mail.send.dlq` + DLQ 리스너, 60초 복구 스위퍼 | 포이즌 메시지·중간 사망이 영구 고착으로 남지 않음 |
| 인덱스 | `(campaign_id, status)` 복합, 토큰 인덱스, 예약·A/B 부분 인덱스 | 완료 판정 EXISTS·토큰 조회가 인덱스로 |
| 관측 | Micrometer → Prometheus → Grafana 6패널, CloudWatch SES 경보 3종 | 처리량·큐 깊이·스로틀을 상시 확인 |

**없는 것**: 캐시(억제 목록 블룸필터 포함), 읽기 전용 DB 복제본, 테이블 파티셔닝·보존 정책,
JDBC 배치 INSERT, 서버 다중화, 공개 경로 속도 제한.

## 3. 한계와 위험

영향이 큰 순서.

### 3.1 SES 할당량이 가장 먼저 막힌다
- 근거: [OPS-MANUAL.md](OPS-MANUAL.md) 경보 표 — 일일 할당량 50,000, 경보 임계 40,000.
- 플랫폼 전체가 나눠 쓴다. PRO 플랜 한 곳의 **월** 한도가 이미 50,000통이다.
- 초당 발송 한도는 어느 문서에도 기록이 없다 → SES 콘솔 Account dashboard 에서 확인 필요.
- 코드 처리량(개발 PC 157.7 msg/s)이 할당량 평균(약 0.6 msg/s)보다 두 자릿수 이상 크다.
  즉 지금은 워커가 아니라 계약이 병목이다.

### 3.2 모든 구성요소가 한 벌뿐이다
- Postgres·RabbitMQ·Kafka·api·worker 가 전부 복제 없이 1개, 서버도 1대.
- 코드는 다중화 가능하게 짜여 있다 (무상태 JWT, claim 기반 동시성, 스케줄러도 claim 으로 중복 실행 안전).
  배포 구조만 한 대다.
- 컨테이너 `mem_limit` 합계 4,224m 가 노드 메모리 4,096m 를 이미 넘는다. 서비스 추가 여지가 없다.

### 3.3 메시지 1통당 DB 왕복이 10회 안팎
`MailDispatchService.dispatchOne` 기준 (리스트 캠페인):

| 순서 | 쿼리 |
|---|---|
| 1 | 메시지 조회 |
| 2 | 캠페인 조회 |
| 3 | 억제 목록 존재 확인 |
| 4–5 | 토큰버킷 INSERT … ON CONFLICT + 차감 UPDATE |
| 6 | claim UPDATE |
| 7 | 연락처 조회 (개인화 변수) |
| 8 | finish 조건부 UPDATE |
| 9 | QUEUED → SENDING 표시 |
| 10 | 남은 메시지 EXISTS (+ 비었으면 완료 UPDATE) |

- 캠페인·연락처 조회는 같은 캠페인 안에서 매번 반복된다 → 캐시 후보.
- 억제 확인은 로드맵 ⑤(블룸필터)가 미착수.

### 3.4 DB 연결 풀이 기본값이다
- api·worker 모두 Hikari 설정이 없어 기본 `maximumPoolSize` 10.
- 워커 소비자는 최대 16개. `dispatchOne` 은 트랜잭션으로 SMTP 전송을 감싸지 않아 교착은 아니지만,
  동시성을 올릴수록 연결 대기가 늘어난다.

### 3.5 INSERT 가 한 건씩 나간다
- 모든 엔티티가 `GenerationType.IDENTITY` → Hibernate 가 JDBC 배치를 끈다.
- 팬아웃 1,000명 페이지 = INSERT 1,000번 (4절에서 상세), 이벤트 프로젝션도 1건씩 INSERT.
- 로드맵 Tier 3 "IDENTITY → 시퀀스" 항목.

### 3.6 Kafka 파티션 1개·복제 1
- `mail.events` 는 `partitions(1).replicas(1)`. 프로젝션 소비자가 사실상 1개라 오픈·클릭 반영 속도의 상한이다.
- 브로커가 죽으면 그 사이 발행 실패분은 재전달이 없다 (상태의 진실은 Postgres 라 발송 자체는 무관).

### 3.7 발송 기록 테이블이 계속 커진다
- `mail_messages`·`email_events` 에 파티셔닝·보존·아카이빙이 없다.
- 이번 달 발송량(`countSentByWorkspaceSince`)은 캠페인 등록·발송 전 확인·대시보드마다 돈다.
  조건이 `status = SENT and updated_at >= 월초`인데 `updated_at` 인덱스가 없고, `status` 인덱스는
  SENT 가 대부분이라 선택도가 낮다 → 행이 쌓일수록 느려질 구조.
- 대시보드 일별 집계도 같은 테이블을 기간으로 훑는다.

### 3.8 공개 경로에 속도 제한이 없다
- nginx `limit_req` 는 `/api/auth/` 에만 (IP당 2r/s, burst 10).
- 추적 픽셀·클릭·수신거부·구독 API·SNS 웹훅은 Cloudflare 기본 방어뿐.
- 추적 픽셀 1회 = 토큰 인덱스 조회 1회 + Kafka 발행 1회. 대량 요청이 들어오면 그대로 DB 로 간다.

## 4. 팬아웃의 DB 부하

### 무엇이 INSERT 되는가
수신자 1명당 `mail_messages` **1행**. 메일 본문은 들어가지 않는다.

| 컬럼 | 내용 |
|---|---|
| `campaign_id`, `recipient`, `contact_id` | 누구에게 어느 캠페인을 |
| `status`, `attempts`, `error_message`, `updated_at` | 발송 상태 |
| `unsub_token`, `tracking_token` | 수신거부·추적용 무작위 UUID 2개 (INSERT 시점에 생성) |
| `variant` | A/B 안 (A/B 캠페인만) |

제목·본문은 캠페인 행에 한 번만 스냅샷으로 저장되고, 발송 리스너가 보내는 순간
`TemplateRenderer` 로 수신자별 변수(`{{name}}` 등)를 치환해 만든다. 100만 명 캠페인도 본문은 1벌이다.

### 1,000명 페이지 하나의 DB 작업
| 작업 | 횟수 |
|---|---:|
| 캠페인 상태 확인 (중단 여부) | 1 |
| 연락처 페이지 조회 (멤버십 조인 + 리스트 수신거부 제외, keyset) | 1 |
| 억제 주소 일괄 조회 | 1 |
| 메시지 INSERT | 1,000 |

팬아웃 시작 시 claim·재개 커서 조회가, 참여도 세그먼트 캠페인이면 180일 참여 집계 2회가 한 번씩 더 붙는다.

### 부하가 있는가 — 있다. 다만 가장 큰 부하는 아니다
- **쓰기 비용이 행 크기보다 인덱스에서 온다.** `mail_messages` 에는 인덱스가 6개
  (PK, status, campaign_id, unsub_token, tracking_token, (campaign_id, status)) — INSERT 1건마다 6곳을 쓴다.
  토큰 두 개는 무작위 UUID 라 인덱스의 아무 위치에나 들어가 페이지 분할과 랜덤 I/O 가 잦다.
- **발송 단계가 팬아웃보다 DB 를 더 쓴다.** 팬아웃이 1,000행을 넣으면 워커가 곧바로 그 1,000건을
  건당 약 10쿼리로 처리한다 → 팬아웃 1,000문장 대비 발송 약 10,000문장. 둘은 같은 Postgres 에서 동시에 돈다.
- **상태 전이마다 행이 새로 쓰인다.** `status` 가 인덱스 컬럼이라 PENDING→SENDING→SENT 갱신은
  Postgres 의 HOT 갱신이 불가능하다. 메시지 1통이 끝날 때까지 힙 튜플 3개와 인덱스 항목 약 18개가 생기고,
  죽은 튜플은 autovacuum 이 치운다. 대형 캠페인 직후 vacuum 부하가 몰릴 수 있다.
- **이미 들어간 완화책**: OFFSET 없는 keyset 페이지, 페이지 크기 고정(메모리 일정), 억제 주소를
  페이지당 1쿼리로 일괄 판정해 큐에 안 넣음, 본문 미저장으로 행이 작음.
- **소요 시간 추정**: 팬아웃만 잰 기록은 없다. 같은 작업(INSERT + 발행)을 요청 안에서 하던 수정 전
  측정이 1명당 2.5~3ms였으므로, 비용이 같다면 10만 명 약 4~5분, 100만 명 약 40분 이상이다
  (요청 밖에서 도니 사용자 응답과는 무관).

### 줄일 수 있는 방법 (착수 시 측정으로 순서 확정)
1. **배치 INSERT** — ID 를 시퀀스로 바꾸고 `hibernate.jdbc.batch_size` + `reWriteBatchedInserts`.
   페이지당 1,000문장 → 수 문장. 가장 큰 단일 개선 후보.
2. **인덱스 재검토** — `idx_msg_status` 단독 인덱스는 SENT 가 대부분이라 선택도가 낮고, 복합 인덱스와 겹친다.
   제거하면 INSERT·상태 전이마다 쓰기 1곳이 준다. 제거 전 실행 계획으로 사용처 확인 필요.
3. **토큰 인덱스 비용** — 무작위 UUID 대신 시간 순 정렬 가능한 형식을 쓰면 인덱스 삽입 위치가 모인다.
4. **발송 단계 왕복 줄이기** — 캠페인·연락처 조회 캐시, 억제 블룸필터(로드맵 ⑤).

## 5. 권장 순서 (나중에 진행)

| 순서 | 작업 | 이유 |
|---|---|---|
| 1 | 운영 노드에서 10만 명 캠페인 드레인 재측정 (팬아웃 소요 시간 포함) | 모든 판단의 기준선. 하드닝 이후 수치가 없다 |
| 2 | SES 초당 한도 확인, 할당량 증설 신청 시점 정하기 | 실제 상한. 증설 심사에 시간이 걸린다 |
| 3 | Hikari 풀 크기 명시 (worker 동시성과 맞춤) | 설정 한 줄, 1번 측정 결과로 값 결정 |
| 4 | 배치 INSERT (IDENTITY → 시퀀스) | 팬아웃 쓰기 왕복 대부분 제거 |
| 5 | 월 발송량 집계 인덱스 또는 사용량 카운터 테이블 | 테이블 증가에 따라 등록·대시보드가 느려지는 것 방지 |
| 6 | 공개 경로 속도 제한 (추적·구독 API) | 트래픽 폭주가 DB 로 직행하는 것 방지 |
| 7 | `mail_messages`·`email_events` 보존 정책·파티셔닝 | 장기 성장 대비 |
| 8 | Kafka 파티션 확대 | 오픈·클릭 반영이 밀릴 때 |
