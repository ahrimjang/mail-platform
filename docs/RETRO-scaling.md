# 병목은 측정이 찾는다 — 발송 파이프라인 확장 회고

> 이 프로젝트의 확장성 작업을 관통한 원칙은 하나였다: **"확장 가능하다"고 주장하지 말고,
> 측정으로 병목을 찾고, 고치고, 같은 조건에서 재측정해 숫자로 증명한다.** 이 글은 그
> 원칙이 실제로 어떻게 굴러갔는지 — 예측이 맞은 곳, 틀린 곳, 만들었다 되돌린 곳까지 —
> 시간순으로 남기는 기록이다. 수치 원본: [loadtest/RESULTS.md](../loadtest/RESULTS.md).

## 1. 측정이 첫 번째 병목을 지목하다 — 캠페인 생성이 O(N)

k6로 기준선을 재자마자 설계 원칙 위반이 수치로 드러났다. "API는 수신자 수와 무관하게
즉시 반환한다"가 이 시스템의 1원칙인데, **캠페인 생성이 수신자 수에 선형**이었다:
1천 명 3.3초, 5천 명 12.1초 — 외삽하면 100만 명은 40분. `create()`가 요청 스레드에서
수신자 행 N개를 INSERT하고 잡 N개를 발행하고 있었기 때문이다.

**해법**: 생성은 **팬아웃 잡 1개만 발행**하고 즉시 반환. 실제 확장은 워커가 keyset
스트리밍 배치(OFFSET 없이 마지막 id 기준)로 수행하고, `QUEUED→EXPANDING` 원자적
claim으로 중복 팬아웃을 막았다. 캠페인 상태에 `EXPANDING`이 추가된 게 이때다 —
팬아웃 도중 "먼저 나간 몇 건이 다 끝나서" 조기 COMPLETED 되는 것을 상태 게이트로 막는다.

**결과**: 1천~10만 명 모두 생성 **40~66ms 상수** — 12.1초에서 약 240×, O(N)→O(1).

## 2. 예측이 틀렸다 — 병목은 SMTP가 아니라 DB 왕복

다음 병목 후보로 모두가 SMTP를 의심했다. 측정은 아니라고 했다: MailHog(로컬 SMTP)를
로깅 발송기로 바꿔도 처리량이 20.5→24.5 msg/s, **+20%뿐**이었다. 진짜 병목은 메시지
1건당 DB 왕복 — 특히 매 발송 뒤 완료 판정이 상태별 COUNT 7개를 돌리고 있었다.

워커 증설 실험도 직관을 배신했다. 2대로 늘려도 1.56×(서브선형) — 워커당 리스너 동시성이
1이라서, 기계를 늘리기 전에 **프로세스 안의 병렬성**부터 열어야 했다.

**해법 세 가지**: 리스너 동시성 1→8, 완료 판정을 7×COUNT에서 **EXISTS 1개**로
(`hasPendingOrSending`), 복합 인덱스 `(campaign_id, status)`.

**결과**: 단일 워커 **20.5 → 157.7 msg/s (~7.7×)**, E2E 244초 → 31.7초. 워커 2대(32
msg/s)보다 1대+동시성 8이 4.9× 빠르다 — "증설보다 동시성이 싼 레버"라는 교훈을 수치로.
그리고 동시 소비자 12개에서도 **이중발송 0** — 원자적 claim(PENDING→SENDING 조건부
UPDATE)이 부하에서 검증된 순간이다.

## 3. 멀티테넌시가 만든 새 병목 — noisy neighbor

SaaS 전환(V16) 후 새 문제가 생겼다: 모든 테넌트가 발송 큐 하나를 공유하므로, A사의
100만 건 뒤에 B사의 10건이 줄을 선다.

**해법**: 워크스페이스별 토큰버킷. 설계에서 갈린 결정 두 개가 핵심이다.

- **Redis 대신 Postgres** — 로드맵 초안은 "워커 간 공유 상태는 Redis"였지만, 이
  저장소의 동시성 문제는 전부 "원자적 조건부 UPDATE" 한 문장으로 풀려 있었다(발송
  claim, 팬아웃 claim, 예약 릴리스, A/B 승자). 토큰버킷의 리필+차감도 같은 패턴으로
  UPDATE 한 문장에 담으면 새 인프라 없이 워커 N대가 버킷 하나를 공유한다. 병목이
  오면 `SendRateLimiter` 포트 뒤에 Redis를 꽂는다 — 헥사고날이 열어둔 퇴로.
- **거절된 메시지는 TTL 파킹 큐로** — nack 재큐는 hot loop, 리스너 sleep은 소비자
  슬롯 잠식. 소비자 없는 큐에 TTL 1초 + dead-letter로 발송 큐 복귀를 걸면, 한도 초과
  테넌트의 메시지만 비켜서고 다른 테넌트는 그대로 흐른다. 토큰 확인은 **claim보다
  먼저** — 순서를 바꾸면 거절된 메시지가 SENDING에 갇혀 stale 창(2분)을 기다린다.

**결과**: rate=3 설정 시 실효 **정확히 3.0 msg/s**, 그 백로그가 도는 중에 무제한
테넌트의 10건은 **0.3초** 완료. noisy neighbor 소멸.

**덤으로 얻은 교훈**: 이 실측 단계에서 단위 테스트가 놓친 실결함이 나왔다 — 무제한
워크스페이스(rate NULL) 경로의 `Stream.findFirst()` NPE로 메시지가 전부 DLQ행.
rate가 설정된 경로만 커버한 mock 테스트는 통과했었다. **측정은 성능만 재는 게 아니라
정확성의 마지막 그물이다.**

## 4. 계기판 달기 — 실측을 상시 관측으로

부하테스트는 "한 번 재는" 도구다. 마지막 축은 그 수치를 **상시 계기판**으로 승격하는
것: Micrometer(계측은 infra 어댑터에만 — 코어는 모름) → Prometheus → 파일 프로비저닝
Grafana 6패널. 스로틀 실측이 그래프로 재현되는 것(토큰 거부율 ≈ 파킹 재큐율 두 선이
겹쳐 움직임)으로 검증을 마쳤다. 대시보드가 파일이라 `down -v` 후에도 같은 화면이
뜨고, 패널 변경이 git diff로 리뷰된다.

## 5. 만들었다 되돌린 것들 — 회수도 기록이다

- **메시지 전이 이력 로그(V19 1차)**: "대기열 등록→취소 이력을 보고 싶다"로 시작해
  append-only 로그+타임라인 UI까지 만들었지만, 비용을 정직하게 계산하니(행 수 2배,
  발송 핫패스 INSERT +1 — IDENTITY라 미배치, 집계 스캔 2배) 지금 규모에선 가치보다
  비쌌다. **전체 회수**하고, 재도입 조건(배치 INSERT + 보존 정책)을 로드맵에 남겼다.
- **BYO 커넥터 과금(V16→V20)**: "고객 계정에 인프라를 연결해 정산 문제를 소멸시킨다"
  는 모델로 출발했지만, 미터링과 rate limit이 완성되자 BYO의 명분 자체가 사라졌고
  온보딩 마찰과 발신 평판 통제 문제가 남았다. **플랫폼 소유 인프라 + 발송량 과금**으로
  번복하고, 번복 경위를 원래 결정 바로 옆에 기록했다.

두 번 모두 코드보다 오래 남는 산출물은 **판단의 기록**이었다.

## 최종 스코어보드

| 병목 | Before | After | 수단 |
|---|---:|---:|---|
| 캠페인 생성 | 5천 명 12.1초 (O(N)) | 40~66ms 상수 (O(1)) | 비동기 팬아웃 + keyset 배치 |
| 드레인 처리량 | 20.5 msg/s | 157.7 msg/s | 동시성 8 + EXISTS + 인덱스 |
| 수평 확장 정확성 | — | 동시 소비자 12, 이중발송 0 | 원자적 조건부 UPDATE claim |
| noisy neighbor | 공유 큐 대기 | 무제한 테넌트 0.3초 완료 | Postgres 토큰버킷 + TTL 파킹 큐 |
| 관측 | 일회성 k6 | 상시 6패널 + LAG | Micrometer→Prometheus→Grafana |

한 줄 요약: **측정 → 수정 → 재측정의 루프를 다섯 번 돌렸고, 그 중 두 번은 직관이
틀렸음을(SMTP 병목설, 워커 증설론), 한 번은 테스트가 못 잡은 결함을 측정이 잡았다.**
