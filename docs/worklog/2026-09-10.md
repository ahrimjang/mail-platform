# 작업 로그 — 2026-09-10

평판 방어의 마지막 두 조각을 실운영에 붙였다. **바운스 웹훅**(사후 방어)을 실제
바운스로 실증했고, **원클릭 수신거부 헤더**(사전 방어)를 실었다. 그리고 웹훅이 켜지자
곧바로 나온 질문 — "억제된 주소를 어디서 보나" — 에 답하는 화면을 만들었다.
(직전 로그 이후 9일 오후 작업을 포함한다.)

## 오늘 한 일 (요약)

### 1. SNS 바운스 웹훅 — 연결과 실증
토픽 ARN 을 서버 `.env` 의 `APP_WEBHOOK_SNS_TOPIC_ARN` 에 넣고, SES Identity 의
Bounce/Complaint 알림을 토픽에 연결한 뒤, **우리 콘솔에서** 시뮬레이터 주소
(`bounce@` / `complaint@simulator.amazonses.com`)로 캠페인을 보냈다.

검증 경로를 정확히 고르는 것이 관건이었다. 발송 경로 셋 중 이 검증에 쓸 수 있는 건
**캠페인 발송 하나뿐**이다 — 테스트 발송은 상관 키가 `"test-send"` 문자열이라 파싱에
실패하고, SES 콘솔의 테스트 메일에는 우리 헤더가 아예 없다. 둘 다 "상관 지을 수 없어"
경고를 내는데, 그걸 보고 설정을 의심하면 원인을 잘못 짚게 된다.

결과: 캠페인 상세에 두 주소가 **바운스**로 표시되고 진단 코드(`550 5.1.1 … user
unknown`, `abuse`)까지 붙었다. 이건 `messages.findById(messageId)` 가 성공했다는 뜻이고,
따라서 `X-Mail-Message-Id` 헤더가 SES 를 왕복했으며("원본 헤더 포함"이 켜져 있다),
같은 조회를 쓰는 억제 분기도 통과했다는 뜻이다. 체인 전체가 처음으로 실데이터로 돌았다.

- 연결 직전, 상관 실패를 **로그로 드러나게** 했다(`3b4af19`). 헤더가 없으면 억제를
  건너뛰는 건 맞다(아니면 전 테넌트 목록이 오염된다). 문제는 그 사실이 화면상 "바운스가
  한 건도 없는 것"과 구분되지 않았다는 점이다 — 배선이 빠져도 징후가 없었다.

### 2. 원클릭 수신거부 헤더 — List-Unsubscribe (`ecf6da0`)
Gmail·야후는 대량 발송자에게 이 헤더를 요구한다. 없으면 수신자는 메일 앱의 "수신거부"
대신 "스팸 신고"를 누르고, 그 컴플레인율은 공유 IP 를 쓰는 SES 계정 전체의 평판에 꽂힌다.

- SMTP 어댑터가 `List-Unsubscribe: <url>` + `List-Unsubscribe-Post: One-Click` 을 붙인다.
  헤더의 URL 은 본문 수신거부 링크와 같은 곳이다.
- `POST /api/unsubscribe/{token}` 이 원클릭(RFC 8058)을 받는다 — 사람이 여는 GET 선택
  화면과 같은 URL, 메서드로 갈린다. **전체 수신거부**로 처리한다: 되물을 화면이 없고,
  리스트 하나만 끊어 다른 메일이 계속 가면 다음번엔 스팸 신고를 누른다. 이미 처리된
  토큰에도 200 — 실패로 답하면 앱이 계속 두드린다.
- `MailSender` 포트의 부가 인자를 `Options(replyTo, listUnsubscribeUrl)` 로 묶었다.
  String 오버로드가 셋으로 늘던 것을 정리. 트랜잭셔널·인증 메일은 `Options.NONE` —
  구독이 아니므로 수신거부 버튼이 뜨면 안 된다.

### 3. 억제 목록 화면 (`c45b25b`)
웹훅이 켜지자 첫 질문이 "억제된 주소를 어디서 보나"였는데, **볼 곳이 없었다.** 수신자
화면의 "수신거부" 필터는 연락처와 조인해 보여주므로 직접 입력으로 보낸 주소(시뮬레이터
주소가 그랬다)는 어디에도 안 나타났고, 억제 저장소에는 개수·사유별 집계만 있고 목록
조회 자체가 없었다.

"애드혹 수신자를 연락처로 자동 등록하자"는 안은 택하지 않았다 — 연락처 한도를 잠식하고,
일회성 주소의 개인정보를 영구 보관하며, 테스트 주소로 명단이 오염된다. 연락처는 운영자가
**의도적으로 관리하는 자산**이지 발송의 부산물이 아니다. 대신 억제 테이블을 그대로
보여준다: `GET /api/suppressions` + 수신자 화면의 "억제 목록" 탭(사유별 요약·검색·해제).
해제 버튼은 바운스·신고로 잡힌 주소에 한해 "풀면 다시 반송돼 평판을 깎는다"고 경고한다.

- 덤: 분석 화면의 "발송 중단 사유"가 `bounce/unsubscribe/manual` 만 알아서 웹훅이 만드는
  `hard_bounce`·`complaint` 를 전부 **"수동"** 으로 찍고 있었다. 라벨을 한 곳(`format.ts`)
  으로 모아 고쳤다.

### 4. 도메인 청구 건 정리
8월 청구서의 `outpaceonline.com` $16 은 **등록 성공 → 삭제 성공** 이력이었다(Route 53
Requests 탭). 즉 등록됐다가 사용자가 삭제한 것 — RDAP 404 는 삭제로 풀려난 결과였다.
등록비는 레지스트리로 넘어가는 비용이라 원칙적으로 비환불이지만, `.com` 의 Add Grace
Period(5일) 안에 삭제됐다면 레지스트라는 손해가 없으므로 요청 ID 두 개를 첨부해 환불
케이스를 넣기로 했다(기대치는 낮게). 앞으로 나갈 비용은 없다.

## 검증
- 헤더 검증을 **두 층으로** 잠갔다: 코어 테스트는 URL 이 어댑터에 넘어가는지, 새
  `infra` 테스트(`SmtpMailSenderTest`, 이 모듈의 첫 테스트)는 그 URL 이 **실제 MIME
  헤더**가 되는지. Docker 가 꺼져 있어 MailHog 대신 택한 방식인데, 서버 없이 전선에
  실리는 헤더를 그대로 보니 오히려 더 결정적이었다.
- 배포 후 라이브: `health 200`, `/api/suppressions → 401`(인증 게이트 뒤에 살아 있음),
  잘못된 토큰의 원클릭 POST → `400`. 억제 목록 탭은 사용자가 운영 계정으로 열어
  시뮬레이터 주소 두 건이 사유와 함께 보이는 것을 확인.

## 배운 것
- **검증 경로를 잘못 고르면 맞는 설정을 의심하게 된다.** 같은 "상관 실패" 경고가 세
  경로에서 나오는데 원인은 전부 다르다. 검증 절차를 안내할 때는 "무엇으로 보내라"만이
  아니라 "무엇으로 보내면 안 되고 왜"까지 적어야 한다.
- **침묵하는 안전장치는 없는 것과 같다.** 상관 실패 시 억제를 건너뛰는 건 옳은 설계였지만
  그 사실이 어디에도 남지 않아, 배선이 빠져도 "바운스 0건"으로 보였다. 방어 로직이 입력을
  못 받는 상태를 관측 가능하게 만드는 것이 방어 로직만큼 중요하다.
- **저장은 됐는데 볼 수 없는 데이터는 운영자에게 없는 데이터다.** 억제는 처음부터 잘
  저장되고 있었다. 화면이 없었을 뿐인데 사용자는 "억제가 되긴 하나"를 의심했다.
- 사용자 제안(자동 연락처 등록)이 가리키는 **문제**는 맞고 **해법**은 부작용이 큰 경우,
  문제를 인정하고 다른 해법을 내는 것이 "반대"보다 낫다.
