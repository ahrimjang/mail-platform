# 작업 로그 — 2026-09-09

가입부터 발송까지의 동선을 사용자 관점으로 훑고, 나온 문제 여섯 갈래를 순서대로
고쳤다. 공통점이 하나 있었다 — **화면은 무언가를 약속하는데 코드가 그 약속을 안
지키고 있었다.** "끌어다 놓으라"는 드롭존에는 드롭 핸들러가 없었고, 자동 저장처럼
보이는 표시 뒤에는 수동 저장뿐이었으며, "이 캠페인으로 시작"은 방금 미리본 안이
아니라 늘 A안을 복사했다.

## 오늘 한 일 (요약)

### 1. 에디터 — 저장 안 한 편집 보호·뒤로가기 목적지 (`72a4f4c`)
에디터 3종은 수동 저장뿐인데 이탈 경고가 **전혀** 없었다. 뒤로 한 번, 새로고침
한 번에 수십 분의 편집이 확인 없이 사라졌다. 더 나쁜 건 표시였다 — 클래스 이름이
`op-autosave` 고 문구는 "저장 전"이라, 자동 저장이 되는 것처럼 읽혔다.

- 기준선 대조로 dirty 를 판정해 탭 닫기·새로고침은 브라우저 확인창으로, 화면 안
  이탈은 확인을 통과해야 진행되게 했다(`outpace/unsaved`). 저장 안 된 상태는
  **"저장 안 됨 — 저장을 눌러주세요"**로 분명히 말한다.
- 뒤로가기가 열린 대상이 있던 화면으로 간다. **이메일을 편집하다 뒤로 누르면
  템플릿 관리로 떨어졌다** — 주 동선이 다른 개념의 목록으로 빠지고 있었다.

켜는 김에 잠복 버그 둘이 드러났다.

- **블록 에디터의 저장이 마지막 인라인 편집을 빠뜨릴 수 있었다.** 저장 직전
  `blur()` 로 커밋한 결과가 클로저의 `blocks` 에는 아직 반영되지 않은 상태에서
  그 값을 직렬화했다. ref 로 최신값을 읽게 고쳤다.
- **텍스트 에디터가 첫 저장 후 `?target=email` 을 잃었다.** 라우트가 바뀌며
  `isEmail` 이 false 로 되살아나, 이후 저장이 `/api/templates/{이메일id}` 로 가서
  엉뚱한 행을 건드릴 수 있었다.

### 2. 수신자 입력 — 가짜 드롭존과 어긋난 파서 (`76d2ff0`)
- **드롭존에 드롭 핸들러가 없었다.** "CSV 파일을 끌어다 놓으라"고 안내해 놓고
  실제로 놓으면 브라우저가 그 파일로 이동해 **작성 중인 폼이 통째로 사라졌다.**
  안내문이 사용자를 사고로 유도하고 있었던 셈이다. 파일을 읽어 주소를 채우게
  하고, 페이지 어디에 놓아도 이동하지 않도록 window 레벨에서 막았다.
- **파서가 구분자로 전부 쪼개 이름 컬럼까지 수신자로 셌다.** 부제는 "이메일, 이름
  컬럼"이라고 CSV 붙여넣기를 권하는데, `a@b.com, 앨리스` 두 줄이면 화면은 4명이라고
  표시했다. 줄 단위로 보고 주소처럼 생긴 토큰만 거둔다.
- 형태가 깨진 주소는 입력 중에 알리고 등록을 막는다. **조용히 빼는 쪽이 더 나쁘다** —
  보냈다고 믿게 두기 때문이다. 도메인 품질(테스트 도메인·오타 후보) 판정은 서버가
  소유하므로 화면에서 흉내내지 않았다.

### 3. 등록 게이트를 작성 전에 알리기 (`76d2ff0`)
게이트 다섯(이메일 인증 → 평판 정지 → 발신 도메인 → 워밍업 → 플랜 한도)이 전부
**마지막 클릭에서 예외로** 터졌다. 리스트 500명을 고르고 "발송 전 마지막 확인"까지
통과한 뒤에야 "첫 발송은 50명까지"를 처음 듣는다.

- `GET /api/campaigns/preflight` 로 같은 판정 재료를 읽기 전용으로 내보낸다. 기존
  게이트 서비스에 조회 메서드만 더했고 **판정 로직은 복제하지 않았다** — 집행은
  여전히 등록 시점 게이트이고 이 값은 안내용이다(신뢰 경계 아님).
- 작성 화면 상단에 인증 필요·정지 사유·워밍업 상한·월 잔여 발송량을 띄우고, 같은
  판정을 `submit` 진입부에서 먼저 해 확인 모달까지 갔다가 거절당하지 않게 했다.
- **발신 이메일을 "아이디 + @도메인" 고정 입력으로** 바꿨다. 힌트는 "서비스 도메인만
  가능"이라고만 알려주고 정작 그 도메인이 뭔지는 안 알려줘, 사용자가 추측해서 넣고
  거절당하는 구조였다.

### 4. 평문 본문이 한 덩어리로 도착하던 문제 (`76d2ff0`)
메일은 항상 HTML 로 나간다(`setText(body, true)`). 그런데 캠페인 작성 화면의 직접
입력 본문은 그냥 `textarea` 라, 평문으로 세 문단을 쓰면 수신자는 **줄바꿈이 사라진
한 덩어리**를 받았다. 가장 쉬운 기본 경로가 가장 조용히 망가지고 있었다.

발송·미리보기·테스트 발송이 같은 변환을 쓰게 하고(셋이 어긋나면 "미리보기는
멀쩡한데 받은 메일은 한 덩어리"가 된다), 규칙은 텍스트 에디터와 공유한다
(`outpace/plaintext`). **초안 저장만 원문을 유지한다** — 감싸서 저장하면 이어서
편집할 때 본문 칸에 태그가 들어차기 때문.

### 5. A/B 결과 반영 재발송 — 사실상 없던 경로 (`b35aeb9`)
승자를 확인한 다음에 할 수 있는 일이 없었다. 상세 화면에는 버튼이 없고, 유일한
통로인 "불러오기"는 **승자와 무관하게 A안을 복사했다** — B가 이겼어도 패자 내용으로
시작해 같은 실험을 되풀이하게 했다. 모달이 A안/B안 미리보기 토글을 제공하면서
적용 버튼은 그 토글을 읽지 않는, 본 것과 다른 것이 들어오는 구조이기도 했다.

- 상세 화면에 **"승자 N안으로 재발송"**(A/B) / "이 내용으로 다시 보내기"를 두고,
  작성 화면이 `?fromCampaign=&variant=` 를 받아 그 안의 내용으로 채운다. 이때
  **A/B 는 끈다** — 이미 판정이 난 실험을 반복할 이유가 없다.
- 불러오기 모달은 미리보는 안을 그대로 적용한다. 승자가 있으면 선택 시 승자 안이
  먼저 열리고, B를 고르면 A/B 쌍이 맞바뀌어 담겨 내용이 유실되지 않는다.

### 6. 첫 사용자 동선 (`b35aeb9`)
신규 워크스페이스는 KPI 가 전부 0 이라 아무 정보를 주지 못했고, 버튼은 "새 캠페인"
하나뿐이라 **이메일도 리스트도 없는 상태로 작성 폼에 도착해 막혔다.** 그 폼의 빈
상태 안내마저 링크가 아닌 그냥 텍스트여서, 클릭할 수도 작성 중 내용을 지키며
다녀올 수도 없었다.

- 대시보드에 첫 발송까지의 4단계(인증 → 수신자 → 이메일 → 테스트 후 첫 캠페인)를
  두고 다음 할 일로 바로 보낸다. 준비가 끝나면 사라진다.
- 빈 상태 안내를 버튼으로 바꾸고, 전부 이탈 확인을 거치게 했다.
- 함께: 테스트 발송의 받는 사람을 본인 주소로 고정(서버가 본인만 허용하는데 입력이
  열려 있어 동료 주소를 넣고 거절당했다), 내용 없으면 버튼 차단(영어 원문 노출
  제거), 안내문의 **MailHog 문구 삭제**(운영 사용자에게 내부 도구 이름이 보였다),
  "발송 큐 등록" 같은 내부 용어를 사용자 언어로.

### 7. 백그라운드 탭에서 멈춰 있던 캠페인 상세 (`b35aeb9`)
새 탭으로 열면 **"불러오는 중"에서 영원히 멈췄다.** 폴링 억제(`document.hidden`)가
초기 조회까지 막고 있었다(목록·대시보드는 첫 `refresh()` 를 무조건 부른다). 첫
조회만 가시성과 무관하게 하고 폴링 억제는 그대로 뒀다.

## 검증
지난번 교훈("수정했다와 운영에서 작동한다는 다르다")을 이번엔 처음부터 절차로 넣었다.

- 새로 만든 순수 함수(수신자 파싱·평문 변환)를 실제 입력으로 직접 돌려 확인.
- **로컬 스택을 띄우고 신규 계정을 만들어 실제 화면으로 여섯 항목을 전부 통과.**
  워밍업 사전 차단(60명 → 50명 안내), 형태 불량 주소 차단, CSV 드롭(이름 컬럼
  제외하고 2명), 이탈 확인창의 취소/확인 분기, 승자 B안 재발송으로 B안 내용이
  들어오는 것까지.
- 평문 처리의 확증은 **MailHog 에 도착한 실제 메일의 HTML** 이었다 — `<p>` 문단과
  `<br>` 이 들어 있는 것을 눈으로 봤다. 화면 안에서만 봤으면 놓쳤을 지점이다.
- 배포 후 라이브에서 `/api/campaigns/preflight` 가 **404 가 아니라 401** 임을 확인
  (엔드포인트가 실렸고 인증 게이트가 걸려 있다는 두 가지를 한 번에 보는 검사).

## 배운 것
- **"안내가 있다"와 "동작한다"는 다르다.** 드롭존은 문구만 있고 핸들러가 없었다.
  약속만 하고 지키지 않는 UI 는 아무것도 없는 UI 보다 나쁘다 — 사용자를 사고 쪽으로
  안내하기 때문이다.
- **집행 게이트를 만들 때 예고 창구도 같이 만든다.** 다섯 게이트가 모두 마지막
  클릭에 몰려 있던 건 각 게이트가 "막는 것"만 생각했기 때문이다. 판정 재료를 읽기
  전용으로 내보내는 조회를 집행 로직 옆에 두면 실패 시점을 앞당길 수 있다.
- **한 화면을 두 개념에 재사용하면 분기를 빠뜨린 자리가 남는다.** 에디터를
  템플릿·이메일이 공유하는데 뒤로가기·라벨·오류 문구·URL 파라미터가 전부 템플릿
  기준으로 남아 있었다. 재사용할 땐 "이 화면이 대상에 따라 달라져야 하는 것"을
  목록으로 뽑아 훑는 편이 낫다.
- **조용히 빼는 것보다 막는 것이 낫다.** 형태가 깨진 주소를 알아서 제외하면 화면은
  깔끔해지지만 사용자는 보냈다고 믿는다. 발송처럼 되돌릴 수 없는 행동에서는
  성가심이 정확함보다 싸다.
