# 작업 로그 — 2026-09-23

팀장 리뷰(9/22)를 치르고, 그 자리에서 나온 방향에 맞춰 **파이프라인의 미뤄 둔 결함을
한 번에 정리**했다. 관통하는 주제는 하나 — **곧 이 저장소를 포크할 계획이라, 지금 남은
결함은 두 저장소에서 각각 고쳐야 한다.** 그래서 "나중에"로 밀어 둔 🔴 을 전부 앞으로 당겼다.
결과적으로 권장 순서 1번의 안전장치 묶음이 전부 닫혔다.
(직전 로그 이후 21·22일 작업을 포함한다.)

## 21일 — 리뷰 준비와 서명키 롤오버

### 클릭 추적 서명키 교체 경로 (`f2b3e95`)

클릭 링크의 HMAC 서명에는 만료가 없다. 받은편지함에 가 있는 메일은 **발송 당시 키로만**
검증되므로, 키가 하나뿐이면 교체하는 순간 과거 발송분의 클릭이 전부 400 이 된다 — 유출돼도
바꾸기 어려운 구조였다.

`TrackingLinkSigner` 가 키 목록을 들도록 바꿨다. **서명은 언제나 현재 키로, 검증은 현재 +
물러난 키 전부로.** 물러난 키는 `APP_TRACKING_PREVIOUS_SIGNING_KEYS`(쉼표 구분)로 주입하고,
옛 캠페인 클릭이 실질적으로 끊긴 뒤 목록에서 빼면 교체가 끝난다.

빈 조각은 걸러낸다 — 후행 쉼표나 미설정으로 빈 키가 목록에 끼면 HMAC 이 빈 키를 거부해
**검증이 통째로 터진다**(모든 클릭이 500). 테스트로 고정했다.

그리고 `APP_TRACKING_SIGNING_KEY` 가 [.env.example](../../.env.example) 에 아예 없어서, 새 서버를
세우면 조용히 `APP_JWT_SECRET` 폴백으로 갔다. 두 변수를 카탈로그에 넣고 교체 절차는
[OPS-MANUAL](../OPS-MANUAL.md) 6절에 적었다.

### 추가 개발 목록에 성능·확장 절 (`3927092`)

대용량 입력 시 Kafka 경로를 짚다 나왔다. 셋 다 현재 규모(157.7 msg/s)에서는 드러나지 않지만,
대형 캠페인에서 순서대로 막히는 지점이다.

- **참여 카운터 핫 로우** — 한 캠페인의 오픈·클릭이 `campaign_engagement_counts` 의 **같은 행
  하나**를 UPDATE 한다. 10만 통 캠페인의 오픈 2만 건이 발송 직후 몇 분에 몰리면 그 행에서
  직렬화돼, 프로젝션 컨슈머를 늘려도 여기서 막힌다.
- **`mail.events` 파티션 확장** — 지금 1개(개발 사이징). 즉 Kafka 의 버퍼 이득만 쓰고 병렬 소비
  이득은 안 쓰고 있다. **위 핫 로우를 먼저 풀어야 효과가 난다**(늘려도 같은 행에서 막힘).
- **팬아웃 saveAll 의 JDBC 배치** — `hibernate.jdbc.batch_size` 미설정이라 1000건 페이지가
  INSERT 1000번으로 나간다.

## 22일 — 팀장 리뷰

발표 자료를 스크립트 기준으로 다시 만들었다(22장, 발표자 노트에 대본 전문). 구성은
①서비스 소개 ②아키텍처 ③MCP 추가 개발. 로컬 스택을 띄워 캠페인 생성 → 테스트 발송 →
리스트 캠페인 팬아웃 → 오픈·클릭 이벤트까지 실제로 돌려 보이며 준비했다.

팬아웃 검증에서 `enqueued_at → expanding_started_at → completed_at` 이 순서대로 찍히는 것으로
`QUEUED → EXPANDING → SENDING → COMPLETED` 전체 상태 머신을 통과한 것을 확인했다. 다만 5명
규모라 EXPANDING 구간이 0.06초 만에 끝나 눈으로는 못 잡았다 — 1000명 단위 페이지 처리라
소규모에선 사실상 순간이다.

리뷰에서 나온 방향: **사내 알림 SaaS(이메일 + SMS + 카카오 + 웹푸시)를 이 저장소 포크로
시작한다.** 계획을 [notification-fork-design.md](../notification-fork-design.md)(`264e6cd`)로
정리했다. "포트만 추가하면 된다"는 기대와 달리 성격이 다른 다섯 층이 섞여 있다 — 그대로
재사용(큐·claim·속도제한·DLQ), 도메인 모델 채널 중립화, 채널별 수신자 모델 신규 설계,
외부 업체 심사(카카오 비즈메시지·통신사 발신번호·VAPID), 사내용 스코프 축소. 착수 순서에서
**포트 추가를 일부러 맨 마지막**에 뒀다.

## 23일 — 포크 전 파이프라인 정리

포크 시점에 남은 결함은 두 곳에서 각각 고쳐야 한다. 그 기준으로 백로그 우선순위를 재정렬하고
(`9740d24`) 🔴 을 순서대로 닫았다.

### 안전 버그 3건 (`a59bf92`)

- **수신거부 푸터·오픈 픽셀 삽입 위치** — 본문 뒤에 그냥 이어 붙이고 있었다. 완성형 HTML 이면
  `</html>` 바깥에 놓여 메일 클라이언트에 따라 통째로 버려진다. 수신거부 수단이 사라지면 법적
  요건이 깨지고 스팸 신고로 이어진다. `TrackingRewriter.appendInsideBody` 가 마지막 `</body>`
  앞에 넣는다(대소문자·공백 변형 포함). 조각 HTML 은 붙일 자리가 없으니 종전대로 뒤에 잇는다.
- **워커 종료 대기 시간** — 리스너 5초·docker 10초인데 SMTP 는 최악 70초(연결 10 + 읽기 30 +
  쓰기 30)까지 간다. 발송 도중 SIGKILL 이 떨어지면 메시지가 SENDING 에 남고, 2분 뒤 stale
  재클레임이 **이미 나간 메일을 한 번 더** 보낸다. lifecycle 80초 · 리스너 75초 ·
  `stop_grace_period` 95초로 순서를 맞췄다 — 셋의 대소 관계가 어긋나면 의미가 없다.
- **운영자 시더 대소문자** — 환경변수 주소를 소문자로 맞춰 조회하는데 가입은 입력 철자를 그대로
  저장한다. `findByEmailIgnoreCase` 로 바꿨는데, **이건 증상이고 원인은 따로 있었다**(아래).

### 스팸 신고율 별도 정지 축 (`72920a5`)

스팸 신고가 바운스와 같은 바구니에 담겨 10% 임계를 함께 썼다. SES 는 계정 컴플레인율 0.5% 를
정지선으로 보므로, 그 기준에 묻어 두면 **SES 가 우리 계정을 정지시킨 뒤에야 우리 가드가 켜진다.**

축을 둘로 나누고 하나만 넘어도 정지시킨다.

| 축 | 조건 |
| --- | --- |
| 바운스 | 시도 50건 + 비율 10% |
| 스팸 신고 | 시도 200건 + **신고 3건** + 비율 0.3% |

신고 축의 하한을 더 높인 이유는 분모가 작을 때 신고 한 건이 바로 임계를 넘기기 때문이다 —
50건 중 1건이 이미 2% 라, 표본·절대 건수 하한이 없으면 소량 발송자가 우연으로 정지된다.
신고 수는 억제 목록의 `reason='complaint'` 를 센다. `BounceService` 가 이미 그렇게 적고 있어
**별도 집계 테이블도 마이그레이션도 필요 없었다.**

### 이메일 본문 검증 (`ef63102`)

발송 시점이 아니라 **저장 시점**에 본다. 문제를 고칠 수 있는 사람이 화면 앞에 있는 순간이
그때뿐이라서다 — 발송 때 걸러도 캠페인은 이미 등록됐고 수신자는 기다리고 있다.

- **거부(400)**: `<script>`·`<iframe>`·`<form>`. 메일 클라이언트가 어차피 지우고 스팸 필터는
  감점하므로 살려둘 이유가 없다.
- **경고**(저장은 되고 `EmailDraftView.warnings` 로 반환 → 에디터 상단 배너):
  ①기본 제공이 아닌 변수는 빈칸으로 나감 ②`{{고객명}}` 처럼 렌더러 문법(영문·숫자·밑줄)에
  안 맞는 표기는 **중괄호째 그대로 발송** — 빈칸보다 나쁜 결과라 ①과 따로 알린다
  ③102KB 초과 시 Gmail 잘림(잘리면 아래쪽 수신거부 링크가 사라진다).

②는 처음 구현에서 빠뜨렸다가 실제 API 로 확인하다 발견했다. 백로그가 예로 든 바로 그 사례였다.
컨트롤러가 아니라 저장 서비스가 부르므로 **MCP 경로로 들어와도 같은 검사를 통과한다.**

### DMARC — 항목이 틀렸다 (`20ce229`)

"SPF·DKIM 은 있으나 DMARC 기록이 없다"고 적어 뒀는데, 실측해 보니 있었다.

```
_dmarc.outpacemail.com  TXT  "v=DMARC1; p=none; rua=mailto:..."
```

Gmail 대량 발신자 요건은 이미 충족한다. 다만 `p=none` 은 관찰 모드라 **사칭 방어 효과는 0** 이라,
정책 강화(`quarantine` 승급)를 🟡 로 분리했다. 리포트를 몇 주 받아 정상 발송이 전부 통과하는
것을 확인한 뒤 올려야 한다 — 순서를 건너뛰면 우리 메일이 스팸함으로 간다.

### 계정 이메일 정규화 (V37, `9bb07e0`)

시더 대소문자를 고치다 원인을 찾았다. `uk_users_email` 이 평범한 `UNIQUE (email)` 인데 가입·
로그인 모두 입력 철자를 그대로 썼다. 그래서 **`User@x.com` 으로 가입한 사람은 `user@x.com` 으로
로그인하지 못했고**, 두 주소가 서로 다른 계정으로 각각 가입될 수 있었다. 모바일 키보드의 자동
대문자화로 흔히 밟는 경로다.

`User.normalizeEmail`(trim + 소문자)을 쓰기·조회 양쪽에 건다 — 가입, 로그인, 구글 로그인,
비밀번호 재설정, 멤버 추가. 한쪽만 하면 기존 행을 못 찾으므로 양쪽이 짝이다.

**로그인 잠금 키도 같이 정규화했다.** 원본 철자를 키로 쓰면 `user@x` / `User@x` / `uSer@x` … 로
계정 축 잠금(5회)을 철자 수만큼 우회할 수 있었다 — IP 축만 남아 실질 방어가 약해진다.

V37 은 기존 행을 내리고 `lower(email)` 유니크 인덱스로 재발을 막는다. 내리기 전에 대소문자만
다른 중복을 검사해 있으면 **RAISE EXCEPTION 으로 배포를 멈춘다** — 어느 계정을 살릴지는 사람이
정할 문제고, 조용히 병합하면 한쪽 워크스페이스의 소유자가 사라진다. 운영 DB 는 사전 조회에서
중복 0건임을 확인하고 진행했다.

로컬 검증: 대문자 행을 심어 마이그레이션이 내리는 것, 세 가지 철자(소문자·혼합·전부 대문자+공백)로
모두 로그인되는 것, 대문자 변형 재가입이 409 로 막히는 것까지 확인했다.

MCP 설계가 V37 을 예약해 뒀는데 이게 먼저 나가면서 **MCP 는 V38, AI 작성 설계는 V39** 로 문서
번호를 옮겼다(`b1e72a6`).

## 배운 것

- **증상만 고치면 원인이 남는다.** 시더 대소문자는 백로그에 적힌 대로 한 줄 고치면 끝이었지만,
  같은 뿌리에서 "대문자로 가입하면 로그인 불가"라는 훨씬 심각한 버그가 나왔다. 좁은 항목을
  고칠 때도 **왜 그런 상태였는지**를 한 번 더 묻는다.
- **보안 구멍은 옆에 붙어 있다.** 이메일 정규화를 하다 로그인 잠금 키가 원본 철자인 것을 봤다.
  같은 값을 쓰는 다른 자리를 훑는 것이 별도 점검보다 싸다.
- **임계는 자릿수가 다르면 축을 나눠야 한다.** 바운스 10% 와 컴플레인 0.5% 를 한 바구니에 담는
  순간, 느슨한 쪽이 기준이 되어 촘촘한 쪽은 사실상 없는 장치가 된다.
- **작은 표본에서 비율 임계는 위험하다.** 0.3% 를 50건 표본에 적용하면 한 건이 2% 다.
  비율에는 표본 하한과 절대 건수 하한이 같이 붙어야 한다.
- **포크 계획이 우선순위를 바꾼다.** 같은 결함이라도 "곧 복사될 코드"에 있으면 값이 두 배다.
  기술 부채의 급함은 코드 자체가 아니라 **앞으로의 계획**이 정한다.
- **문서에 적힌 사실도 만료된다.** DMARC 는 "없다"고 적힌 채 남아 있었다. 설정 상태처럼 외부에서
  바뀔 수 있는 것은 항목을 볼 때마다 실측한다(`nslookup` 한 줄이면 됐다).

## 남은 작업

- **DMARC 정책 강화** — `rua` 리포트 몇 주 관찰 후 `p=none` → `quarantine`. 루트 SPF 에 SES
  include 가 없는 것도 같이 확인(받은 메일의 `Authentication-Results` 로 판단).
- **MCP 0~2단계** — 당분간의 초점. 공개 REST 확장 + V38 키 테이블 → 조회·초안 도구 →
  발송·중단 도구와 안전장치.
- **참여 카운터 핫 로우** — 포크 후 채널이 늘면 같은 카운터에 트래픽이 몇 배로 얹힌다.
  성능 항목 셋 중 이게 먼저다.
- **발신 도메인 인증** — 포크가 확정되면 이메일 전용이 아니라 채널 중립(SMS 발신번호·카카오
  채널 포함)으로 설계하는 편이 중복 작업을 줄인다.
- 운영자 콘솔 개시(서버 `.env` 의 `APP_PLATFORM_OPERATORS`), 검색 등록은 그대로 남아 있다.
