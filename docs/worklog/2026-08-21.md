**서비스가 실도메인에서 무중단 자동 배포로 굴러가는 상태**가 됐다. 배포 자동화(GitHub
Actions→ghcr→서버 pull)를 붙이고, 그 첫날 배포 파이프라인이 일으킨 전면 다운(521)을

`support@`/`abuse@` 채널을 개통했다. SES 프로덕션 액세스는 1차 거절 → 재신청 대기.

## 오늘 한 일 (요약)

### 1. 배포 자동화 — master 푸시가 곧 배포 (`7d629e3`, `79075ca`)
GitHub Actions가 이미지 3종(api/worker/front)을 빌드해 ghcr 에 올리고 서버에 SSH 로
`compose pull + up -d --no-build`. **서버에서 빌드가 사라져** 4GB 노드의 메모리 경합
(OPS-LOG 1호)이 구조적으로 해소됐다. sha 태그 병행 푸시로 즉시 롤백 가능, 연속 푸시는
`concurrency` 로 직렬화. 준비물: 저장소 시크릿(호스트·SSH 키), 서버의 ghcr
`docker login`(read:packages 토큰) 1회.
- 후속(`79075ca`): **문서만 바뀐 푸시는 배포 스킵**(`paths-ignore`) — 같은 코드라도
  재빌드는 이미지 다이제스트를 바꿔 api 컨테이너를 교체하므로(수 분 /api 502),
  README 한 줄에 API 순단이 따라오던 낭비를 제거.

### 2. 배포발 전면 다운(521) — 복구와 구조적 해소 (`27e0d87`, `9ebf76c`)
문의처 교체 배포에서 api 재기동이 평소의 8배(234초) 걸려 헬스체크 예산(190초)을
초과 → front/worker 가 `depends_on: healthy` 에 묶여 기동 포기 → **정적 페이지까지
전면 다운 10분**. 이어진 배포는 멀쩡한 kafka 가 unhealthy 오탐으로 실패.
세 사건의 뿌리는 하나 — **2vCPU 노드에서 배포 순간의 CPU 포화**.
- front 의존을 `service_started` 로: api 가 늦어도 랜딩·약관은 산다. 최악이 "/api 만
  잠시 502"로 국한 — 전면 다운 경로 자체가 제거됐다. worker 는 validate 실패 시
  restart 정책으로 자가 회복.
- api 헬스 예산을 실측 기반 7분으로. kafka 헬스체크는 검사마다 JVM 을 띄우던
  `broker-api-versions.sh` 를 `/dev/tcp` 포트 응답으로 교체 — 오탐과 상시 CPU 낭비를
  함께 제거. 교훈: **헬스체크는 검사 대상보다 가벼워야 한다.**
- 전 과정 [OPS-LOG.md](../OPS-LOG.md) 2호에 기록. 수정 후 배포에서 사이트 무중단 실증.

### 3. 콘텐츠 정책 체계 — 약관 개정 + 신고/문의 채널 (`954b4b9`, `71d29dd`)
스티비 약관 개정(구독결제 콘텐츠 기준)을 계기로 우리 구멍을 점검: 기술적 정지 장치
(바운스율 자동 정지 V32)는 있는데 **집행할 약관 근거가 한 문장**뿐이었다.
- 제9조 신설: 금지 콘텐츠 6종(불법 재화·피싱·발신 위장·권리 침해·음란/도박/금융사기·
  증오 조장) + 조치 3단계(제한·통지→소명→해지, 중대 사안 즉시 해지).
- 제10조 신설: **콘텐츠 작성 주체도, 회원-수신자 간 법률관계의 당사자도 아님** —
  "검열"이 아니라 중개자 지위 + 사후 제재가 플랫폼의 올바른 위치라는 판단.
- Cloudflare Email Routing 으로 `support@`(문의)·`abuse@`(신고) 개통, 전 페이지의
  개인 지메일 노출 제거. 신고 채널 분리는 SES 재심사의 실증 근거도 된다.
- 함정 실측: 전달 메일은 지메일 스팸함행이 잦다(포워딩 숙명) — 스팸 예외 필터로 해결.
  본인→본인 테스트는 Message-ID 중복 제거로 안 보인다(Activity Log 로 교차 검증).

### 5. SES 프로덕션 액세스 — 1차 거절과 재신청
거절 사유 비공개지만 유력 원인은 **신청 시점에 사이트가 빈 도메인**이었던 것.
서비스가 실제로 뜬 지금 상세 사유서(동의 기반 수집·SNS 바운스 자동 억제·워밍업
상한·주소 검증)로 재신청 완료, 심사 대기. 샌드박스에서도 검증된 수신자에게는 발송
가능하므로 SMTP 자격증명 발급·스모크 테스트는 승인 전에도 진행 가능. 플랜 B(Postmark
류)는 SMTP 설정 교체만으로 갈아탈 수 있는 구조라 리스크 낮음.

## 배운 것
- `depends_on: healthy` 는 "의존이 아픈 동안 나도 죽겠다"는 선언 — 사용자 대면
  서비스에는 쓰지 말 것. 헬스 예산은 평시가 아니라 최악 실측 기준.
- 저사양 노드에서는 헬스체크 자체가 부하이자 오탐원이 된다(JVM 스폰형 검사 금지).
- 재빌드는 내용이 같아도 다이제스트를 바꾼다 — "문서 수정 → 컨테이너 교체"라는
  비직관적 경로는 CI 의 paths 필터로 끊는다.
