## 아키텍처 트랙 — 🔴 다섯

### ARCH-3 DLQ 리스너 (`d56560c`)
재시도 3회를 소진한 잡은 DLQ 로 가고 거기서 끝이었다. 메시지는 SENDING 인 채 남고
캠페인은 영원히 "발송 중" — 화면상 "실패 0건"과 구분되지 않았다. 워커에 DLQ 소비자를
두어 FAILED 확정 + 캠페인 완료 판정 + 인앱 알림(캠페인당 1시간 1회)을 한다. 발송 잡과
팬아웃 잡이 같은 DLQ 로 오므로 `__TypeId__`·`x-death` 로 가려내고, **여기서는 절대
예외를 밖으로 내지 않는다** — DLQ 에는 데드레터 목적지가 없어 거부되면 메시지가 사라진다.

### ARCH-1·2·5 복구 스위퍼 (`ef965f0`)
"claim 에 이긴 뒤 죽은" 경우의 복구 경로가 비어 있었다. 재전달된 잡은 claim 에서 져
정상 return 하므로 DLQ 도 안 간다 — 조용한 영구 고착. 60초 스위퍼가 셋을 걷는다:
10분 넘게 EXPANDING(V34 `expanding_started_at`)이면 QUEUED 로 되돌려 팬아웃 재발행
— **팬아웃은 이미 만든 메시지의 최대 contactId 뒤부터 재개**(0부터 다시 돌면 같은
수신자에게 두 번 간다); 릴리스됐는데 잡이 없는 QUEUED 는 재발행 또는(메시지가 없으면)
CANCELED; 10분 넘게 PENDING/SENDING 인 메시지는 재발행 — 승자 확정 뒤 릴리스 실패한
홀드아웃(ARCH-2)도 여기 걸린다. 오탐이어도 재발행은 claim 이 멱등하게 받는다.
create() 의 대상 검증을 저장 앞으로 옮겨 고아를 애초에 안 만들게도 했다.

### ARCH-4 종료 상태 조건부 UPDATE (`fca37d9`)
종료 기록이 blind save 였다 — 늦게 끝난 쪽이 무조건 이겼다. claim 이 찍은 `updatedAt`
을 토큰으로 돌려주고, 종료는 `status = SENDING and updatedAt = claimedAt` 일 때만 쓴다.
바운스 웹훅도 SENT/SENDING 에서만 BOUNCED 로. **중복 발송의 진짜 근원은 타임아웃 없는
SMTP 였다** — 조건부 UPDATE 는 덮어쓰기를 막지만 두 번째 발송은 못 막는다. 연결 10초·
읽기/쓰기 30초를 걸어 어떤 hang 도 stale 창(2분) 안에 끝나게 했다.

## 플랫폼 운영자 콘솔 1차 (/ops)

베타 사용자가 들어오면 첫 문의는 "왜 발송이 정지됐나요"인데, 정지 해제·플랜 조정이 전부
psql 과 `.env` 였다(매뉴얼 5·6절). 자동 정지(바운스율 10%)가 켜져 있으니 이 문의는 반드시
온다. MCP·AI 보다 앞에 뒀다.

- **권한 계층**: 워크스페이스 ADMIN 과 별개인 `users.platform_role`(V35). `APP_PLATFORM_OPERATORS`
  이메일 목록을 기동 시 시드(멱등, 회수 없음 — 환경변수는 부트스트랩, 진실은 DB). 권한은
  매 호출 DB 에서 읽어 회수가 토큰 만료를 기다리지 않는다.
- **테넌트 격리의 유일한 예외**를 한 서비스(`PlatformOpsService`)·한 컨트롤러(`/api/ops`)·한
  패키지에 가뒀다. 진입점마다 `isPlatformOperator()`(403), 워크스페이스는 명시 인자, 변경은
  전부 `platform_audit_log`. AGENTS.md 에 "다른 곳에서 이 서비스를 부르지 말 것"을 규칙으로.
- **조치는 기존 규칙을 그대로 탄다**: 정지는 자동 정지와 같은 컬럼(게이트 체인이 그대로 막음),
  플랜 변경의 속도 상한 클램프는 `Workspace.changePlan()` 으로 도메인에 올려 결제 경로와 공유,
  캠페인 중단은 콘솔 abort 와 같은 조건부 UPDATE. 정지·해제·플랜 변경은 테넌트에 인앱 알림.
- **화면 네 탭**: 워크스페이스(30일 바운스율 높은 순 — 문의 날 곳이 위로, 소유자 이메일 검색),
  캠페인(전 테넌트 검색·중단), 운영 신호(정지·진행 중·24시간 실패/반송/중단), 감사 로그.
  목록 집계는 워크스페이스 수만큼 쿼리하지 않도록 (워크스페이스, 상태) 그룹 쿼리 두 번 +
  역할별 사용자 조회 두 번으로 묶었다.
- `mail-admin` 모듈 제거 — `@SpringBootApplication` 하나뿐인 빈 껍데기였고, :8081 에 JVM 을

## 검증
- 전부 순수 단위 테스트로 잠갔다(코어 340여 건, 워커·infra 첫 테스트 포함). 조건부
  UPDATE 로 바꾸며 "save 를 캡처해 상태를 보던" 테스트를 "finish 인자를 검증"으로 옮겼고,
  "동률 → A 확정" 테스트는 "동률 → 유예"로 뒤집었다 — 테스트가 옛 결함을 의도로 박제하고
  있던 자리다.
- 배포마다 api 가 502→200 으로 돌아오는 것을 확인했다. V34 와 새 JPQL 은 infra 를 api·
  워커가 공유하므로 api 기동이 곧 "쿼리가 파싱됐다"는 증거다.
- 스위퍼·DLQ 가 실제로 고착을 걷는 장면은 운영에서 고착이 생겨야 보인다. 지표
  `mail_recovery_total`·`mail_dlq_received_total` 이 0 이 아닌 값을 찍으면 그때가 첫
  실증이고 동시에 조사 신호다(매뉴얼 2절).

## 배운 것
- **claim 은 반쪽이다.** 원자적 claim 은 "둘이 동시에 시작하는 것"만 막는다. 이긴 쪽이
  죽었을 때의 복구, 끝날 때의 기록, 확정할 때의 근거 — 셋을 같이 설계해야 한 세트다.
- **blind save 는 늦게 온 쪽이 이기는 규칙이다.** 그게 의도인 자리는 거의 없다. 종료
  기록에는 "내가 본 그 행 그대로인가"를 조건으로 붙여야 한다.
- **덮어쓰기 방지와 중복 실행 방지는 다른 문제다.** 조건부 UPDATE 는 전자만 푼다. 후자의
  근원(타임아웃 없는 외부 호출)을 따로 막지 않으면 "기록은 맞는데 메일은 두 번 간" 상태가 된다.
- **판정에는 근거 요건이 있어야 한다.** 표본이 없을 때 기본값으로 확정하는 코드는
  "결정을 내린 것"이 아니라 "결정을 숨긴 것"이다. 미루되 상한을 두고, 상한을 넘겨 확정할
  땐 그 사실을 남긴다.
- **테스트는 결함도 박제한다.** "동률이면 A" 테스트가 통과하고 있었다. 감사 항목을 닫을
  때는 기존 테스트가 무엇을 "의도"로 고정하고 있는지부터 의심한다.
