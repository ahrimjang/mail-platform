# 작업 로그 — 2026-09-16

로컬에서 가입부터 발송·추적까지 한 번에 돌려보는 확인 경로를 만들었고, 거기서 **운영에서만
실패했을 결함**을 하나 찾아 고쳤다 — 시스템 메일에 `From` 헤더가 없었다. 검색 노출용 메타도
비어 있어 같이 채웠다. 관통하는 주제는 하나 — **개발 환경이 관대하면 결함은 운영에서만
드러난다.** MailHog 는 아무 메일이나 받아주므로, SES 가 거부할 메일이 로컬에서는 통과한다.
(직전 로그 이후 14·15일 작업을 포함한다.)

## 14일 — 대용량 트래픽 점검 (`0a3af62`)

"이 구조가 큰 물량을 감당하는가"를 문서로 정리했다. 적용된 기술(큐 분리, 팬아웃 O(1) 등록,
조건부 UPDATE claim, 토큰버킷, 읽기 모델), **측정 공백**(운영 노드에서 끝까지 재본 적이 없다),
위험 순서, 팬아웃이 수신자 수만큼 INSERT 하는 구간의 DB 부하를 적었다. 후속 항목은 로드맵으로
넘겼다 — [REVIEW-scale.md](../REVIEW-scale.md).

## 15일 — 캠페인 집계 읽기 모델 (V36, `cc09208`)

캠페인 목록이 화면을 그릴 때마다 캠페인 수만큼 집계 쿼리를 돌렸다. 오픈·클릭은
`email_events` 전량을 세고 있어서, 이벤트가 쌓일수록 목록이 느려지는 구조였다.

- `message_engagements`(PK `(message_id, type)`) — **첫 반응만** 기록. 같은 사람이 열 번 열어도 1.
- `campaign_engagement_counts` — 캠페인·변형별 카운터. 원장 INSERT 와 카운터 +1 이 CTE 한 문장.
- `campaign_delivery_snapshots` — 끝난 캠페인의 상태 개수를 굳힌다. 완료 후 30분(`COUNT_SETTLE`)이
  지나야 저장하고, 늦은 반송·DLQ 확정·낙오분 발송이 생기면 무효화한다. 버전 조건부 저장이라
  두 요청이 동시에 굳혀도 하나만 이긴다.
- 워커 기동 시 `EngagementReconciler` 가 최근 24시간을 대조해 누락분을 메운다.

로컬 검증: 백필 후 기존 distinct 집계와 **불일치 0**, 같은 메시지 오픈 3회 → 원장 3행·카운터 1,
Kafka 오프셋 0부터 전량 재생 후에도 불일치 0, 반송 웹훅이 스냅샷을 무효로 돌리고 재조회가 다시
굳히는 것, 원장에 직접 넣은 클릭을 워커 재기동 후 리컨실러가 집어가는 것까지 확인했다.

같은 날 [TIMELINE.md](../TIMELINE.md)(`c04fdd6`)로 07-01부터의 흐름을 날짜순으로 묶고,
MCP 연동 설계를 갱신했다(`99a7b3f`) — 마이그레이션 번호를 V37 로 밀고, 기존 평문 API 키를
해시로 옮기는 단계와 운영 콘솔에서의 키 폐기를 0단계로 넣었다. 팀장 리뷰용 자료도 만들었다.

## 16일 — 로컬 발송 E2E 와 `From` 헤더 결함

### 확인 경로

MailHog 는 이미 compose 와 양쪽 앱 설정(`SMTP_HOST` 기본값 `localhost:1025`)에 붙어 있어
새로 연결할 것은 없었다. 대신 **가입 → 인증 메일 수신 → 리스트·수신자 생성 → 이메일 작성 →
캠페인 등록 → 워커 발송 → MailHog 수신 확인 → 추적 링크 호출**을 한 번에 도는 스크립트로
확인했다. 인증 토큰도 MailHog 받은편지함에서 꺼내 쓰므로, 사람 손이 들어가는 자리가 없다.

결과: 수신자 8명 캠페인이 `EXPANDING → COMPLETED`, 발송 8·실패 0, 제목의 `{{firstName}}` 이
수신자마다 치환, 오픈 픽셀과 클릭 링크가 각각 카운터에 1 을 올렸다(V36 경로가 실제로 도는
것까지 여기서 같이 확인됐다). 클릭 링크는 302 로 목적지에 넘겼고, 스크립트가 받은 403 은
추적 엔드포인트가 아니라 리다이렉트를 따라간 바깥 사이트의 응답이었다.

### 찾은 결함 (`483b873`)

MailHog 받은편지함에서 **가입 인증 메일의 발신자 칸만 비어 있었다.** 헤더를 열어보니 `From`
자체가 없고 Return-Path 는 `user@host.docker.internal` 이었다.

원인은 두 층이 맞물린 자리다. `EmailVerificationService`·`PasswordResetService` 가 발신 주소
자리에 `null` 을 넘기고, `SmtpMailSender` 는 그 값이 비면 `setFrom` 을 **건너뛴다**. JavaMail 은
지정하지 않은 헤더를 만들어 주지 않으므로 `From` 없는 메일이 그대로 나간다. MailHog 는 받아
주지만 **SES 는 거부한다** — 운영에서는 가입 인증 메일이 도달하지 못하고, 인증은 캠페인 등록
게이트의 첫 고리라 신규 워크스페이스가 발송을 시작할 수 없는 상태가 된다.

호출부 두 곳을 고치는 대신 어댑터에서 막았다. 발신 주소가 비면 `app.mail.system-from`
(`APP_MAIL_SYSTEM_FROM`, 기본 `no-reply@outpacemail.com`)으로 채운다. **발신 주소 없이 등록된
캠페인도 같은 구멍이었는데** 한 곳을 막아 같이 닫혔고, 앞으로 추가될 시스템 메일도 호출부가
주소를 몰라도 된다. api 와 worker 가 같은 주소로 보내야 하므로 운영 compose 의 두 서비스에
같은 값을 준다.

기존 테스트 하나가 깨졌는데, 그 자체가 설명이 된다. `getReplyTo()` 는 Reply-To 헤더가 없으면
**From 을 대신 돌려준다** — 지금까지 `null` 이었던 것은 Reply-To 가 없어서가 아니라 From 도
없었기 때문이다. 단언을 헤더 직접 검사로 바꾸고, 폴백 검증 두 건을 더했다.

### 검색 노출 (`482c41d`)

`<title>Outpace</title>` 외에 아무것도 없어서 검색 결과와 링크 미리보기가 한 줄로만 나왔다.

- 경로별 title·description·canonical·OG 를 라우터 한 곳에서 갱신한다([seo.ts](../../frontend/src/seo.ts)).
  페이지마다 고치지 않고, 외부 라이브러리도 쓰지 않는다(콘솔의 무의존성 유지).
- **index.html 에 랜딩 기준 정적값을 같이 박았다.** 구글은 JS 를 실행하고 크롤링하지만
  네이버·카카오·페이스북의 미리보기 수집기는 돌리지 않는다 — 훅만으로는 카톡에 링크를 붙였을 때
  아무것도 안 나온다.
- 공개 페이지(랜딩·요금제·가이드·개발자·가입·약관류)만 `index,follow`, 콘솔·로그인·재설정·인증
  경로는 `noindex,nofollow`.
- robots.txt 에서 **`/api/` 를 막았다** — 크롤러가 추적 픽셀을 긁으면 오픈 수가 부풀고,
  수신거부 링크를 따라가면 실제 구독자가 해지된다. 이 서비스에서만 생기는 함정이다.
- sitemap.xml(공개 7개), OG 이미지 1200×630, 요금제 구조화 데이터(현재 가격과 맞춤).

## 검증
- 로컬: 위 E2E 를 수정 전후로 각각 돌려 같은 받은편지함에서 대비를 봤다. 수정 후 인증 메일과
  재설정 메일 모두 `From: Outpace <no-reply@outpacemail.com>`, 캠페인은 자기 발신 주소 유지.
- 단위: infra·코어·워커 전부 통과. 프론트 `tsc -b` 와 운영 빌드 통과.
- 배포(`482c41d`): api 가 502 → 200 으로 복귀, robots.txt·sitemap.xml·og-image.png 200,
  메타·구조화 데이터가 운영 HTML 에 실린 것 확인.
- **운영 발송은 검증하지 않았다** — 실제 메일이 나가야 해서 멈췄다. `no-reply@outpacemail.com`
  이 SES 에서 발송 가능한 주소인지 확인이 남는다.

## 배운 것
- **개발용 대역품은 관대해서 결함을 숨긴다.** MailHog 는 프로토콜을 느슨하게 받아준다. 로컬에서
  "메일이 왔다"는 것은 "운영에서도 나간다"는 뜻이 아니다. 앞으로 발송 경로를 손대면 본문만이 아니라
  **헤더를 직접 확인**한다.
- **비어 있으면 건너뛴다는 선택은 조용한 실패를 만든다.** 폴백이 없을 때 무엇이 되는지를 보고
  결정해야 한다 — 여기서는 "헤더가 빠진 메일"이었고, 그건 어떤 경우에도 유효하지 않았다.
- **막는 자리는 호출부가 아니라 경계다.** 어댑터에서 채우니 발견하지 못했던 세 번째 경로(발신
  주소 없는 캠페인)까지 같이 닫혔다.
- **깨진 테스트가 결함의 증거였다.** `getReplyTo()` 가 `null` 이던 것은 통과 신호가 아니라
  From 이 없다는 증상이었다. 통과하던 단언이 무엇을 의도로 고정하고 있었는지 의심한다.
- **E2E 는 한 번 쓰면 계속 쓴다.** 같은 스크립트가 V36 카운터, 추적 링크 서명, 개인화 치환,
  수신거부 헤더까지 한 번에 훑는다. 화면을 눌러 확인하던 것보다 덮는 범위가 넓다.

## 남은 작업
- **SES 확인 두 가지**: `no-reply@outpacemail.com` 발송 가능 여부(도메인 검증이면 그대로,
  주소 검증이면 `.env` 에 `APP_MAIL_SYSTEM_FROM` 지정), 그리고 할당량 — 09-02 기록은 샌드박스
  (하루 200통)인데 매뉴얼 경보는 50,000 을 전제한다. 샌드박스면 인증 메일은 여전히 검증된
  주소로만 간다.
- **검색 등록**: 구글 서치콘솔·네이버 서치어드바이저에 사이트 등록과 사이트맵 제출. 소유 확인
  메타 태그를 받으면 index.html 에 넣는다.
- **SPA 색인 한계**: 네이버 수집기는 JS 렌더링이 제한적이라 공개 페이지 본문을 못 읽을 수 있다.
  국내 유입이 중요해지면 공개 페이지만 사전 렌더링하는 방향.
- 운영자 콘솔 개시(서버 `.env` 의 `APP_PLATFORM_OPERATORS`), MCP 0단계는 그대로 남아 있다.
