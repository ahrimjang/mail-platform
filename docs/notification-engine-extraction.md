# 발송 엔진 분리 — 그룹 통합 플랫폼의 «알림» 컴포넌트로 들어가는 경우

> 검토 문서. 그룹 통합 관리 콘솔 아키텍처에서 **D·공통 지원 > 알림**(SMS·알림톡·이메일)의
> 이메일 채널을 이 프로젝트에서 떼어 쓸 수 있는지 따져본 결과.
>
> **[notification-fork-design.md](notification-fork-design.md) 와 다른 시나리오다.** 그쪽은
> 이 저장소를 포크해 **독립 제품(사내 알림 SaaS)** 을 만드는 전제고, 이 문서는 **이미 설계된
> 남의 아키텍처 안에 컴포넌트 하나로 들어가는** 전제다. 무엇을 버리고 무엇을 남기는지가 꽤 다르다.

## 전제 — 들어갈 자리

```
통합 관리 콘솔
 └ «subsystem» 공통 플랫폼
    A·인증 (SSO·MFA·세션, IAM)
    B·고객·계약 관리 (고객·조직 / 상품·가격 / 계약·구독 / 이용권·좌석)
    C·서비스 운영 (개통·해지 / 사용량 수집)
    D·공통 지원 (감사 / 파일 / **알림**)   ← 이메일은 여기의 채널 하나
 └ 표준 연동 규격 (↓ 정책 배포 / ↑ 개통 결과·사용량 회신)
 └ CMS · SaaS A · SaaS B · 신규 SaaS
```

**알림의 성격이 지금 제품과 다르다.** 여기서 알림은 B·C 도메인이 이벤트로 호출하는
**트랜잭셔널 통지**(개통 완료, 청구, 계약 만료)다. 사람이 화면에서 문안을 쓰고 대상을 고르는
마케팅 캠페인이 아니다. 이 차이가 아래 분류의 기준이 된다.

## 결론 먼저

**가능하다. 다만 떼는 것은 "이메일 발송 기능"이 아니라 "발송 엔진"이고, 지금 코드의 4분의 1쯤이다.**
나머지는 위 그림에서 이미 다른 컴포넌트가 맡는다.

## 무엇을 떼는가 — mail-core 서비스 분류

서비스 클래스 40여 개를 성격별로 나누면 셋으로 갈린다.

### ① 발송 엔진 — 가져간다

| 클래스 | 하는 일 |
| --- | --- |
| `MailDispatchService` | 발송 핵심. claim → 렌더 → 전송 → 종료 기록 |
| `MailSender`(포트) + SMTP 어댑터 | 실제 전송 |
| `SendRateLimiter` | 테넌트별 토큰버킷 + TTL 파킹 큐 |
| `SuppressionService` | 억제 명단 (재발송 금지) |
| `DeadLetterService` | 재시도 소진분 확정·알림 |
| `RecoveryService` | 고착 복구 스위퍼 |
| `BounceService` | 반송·컴플레인 웹훅 반영 |
| `SendingSuspensionService` | 평판 임계 초과 시 자동 정지(바운스·스팸신고 2축) |
| `SendingWarmupService` | 신규 테넌트 워밍업 상한 |
| `EmailAddressValidator` · `SenderPolicy` | 주소 품질·발신 정책 |
| `TemplateRenderer` | `{{변수}}` 치환 |

### ② 마케팅 캠페인 — 안 가져간다

캠페인·팬아웃·예약 발송, A/B 테스트와 승자 판정, 연락처·리스트·참여도 세그먼트,
분석·대시보드, 오픈·클릭 추적, 에디터·템플릿 관리, 발송 전 프리플라이트, 공개 구독 API.

알림 컴포넌트는 "누구에게 보낼지"를 스스로 정하지 않는다 — B·C 도메인이 지정해서 넘긴다.

### ③ SaaS 운영 — 그 플랫폼이 이미 갖고 있다

| 지금 우리 것 | 그 구조에서 담당 |
| --- | --- |
| `AuthService`·`LoginAttemptGuard`·`PasswordResetService`·`EmailVerificationService` | **A·인증** (SSO·MFA·IAM) |
| `WorkspaceService`·`PlatformOpsService` | **통합 관리 콘솔** |
| `BillingService`·`PlanLimits`·`UsageSnapshotService` | **2차 편익·빌링·정산** |
| `UploadService`·`FileStorage` | **D·파일** |
| 자체 감사 로그(`platform_audit_log`) | **D·감사** |

즉 ③은 걷어내는 게 아니라 **경계를 넘겨주는** 것이다. 남겨 두면 두 곳이 같은 일을 하게 된다.

## 가장 큰 걸림돌 — 모든 발송이 캠페인을 거친다

`TransactionalService` 주석에 그대로 적혀 있다.

> 템플릿을 렌더링한 뒤 **단일 수신자 캠페인으로 감싸** 기존 파이프라인(큐·추적·억제·지표)을
> 그대로 재사용한다.

트랜잭셔널 발송조차 `campaigns` 행을 만든다. `MailDispatchService` 는 제목·본문·발신자·
Reply-To·워크스페이스를 전부 `Campaign` 에서 꺼내므로 **캠페인 없이는 한 통도 못 보낸다.**

**해법은 결합을 푸는 것보다 개명이 낫다.** `Campaign` 을 **"발송 요청(배치)"** 로 다시 이름
붙여 엔진 내부 개념으로 유지한다. "요청 1건 → 수신자 N명 → 메시지 N건"과
`QUEUED → SENDING → COMPLETED` 상태 머신은 알림 엔진에도 그대로 맞는 모델이고, 팬아웃·완료
판정·복구 스위퍼가 전부 이 뼈대 위에 서 있어서 들어내면 같이 무너진다.

## 그 아키텍처에 맞추려면 바뀌는 것

| 지점 | 지금 | 알림 컴포넌트에서 |
| --- | --- | --- |
| **트리거 주체** | 사람이 콘솔에서 작성 | **B·C 도메인이 이벤트로 호출** |
| **테넌시 축** | 가입 = 워크스페이스(외부 고객 자기등록) | 계열사 + 업무 도메인. **콘솔이 프로비저닝** |
| **인증** | 자체 JWT·BCrypt·구글 로그인 | A·인증이 담당 — 전부 제거, 서비스 간 인증으로 대체 |
| **감사** | 자체 감사 테이블 | D·감사로 이벤트 발행 |
| **오픈·클릭 추적** | 마케팅 핵심 지표 | 통지에는 보통 불필요하고 사내 규정에 걸릴 수 있다. 대신 **발송 결과 회신**(그림의 ↑)이 필수 |
| **채널 라우팅·폴백** | 없음(이메일 전용) | **알림 엔진의 핵심** — "알림톡 실패 시 SMS" 같은 대체 경로 |

마지막 줄이 중요하다. **채널 라우팅과 폴백은 지금 코드에 없는, 새로 만들어야 할 층이다.**
우리가 떼어 주는 것은 그 아래 어댑터 하나다.

## 붙는 모양

```
B·고객계약 / C·서비스운영
        │  발송 요청 (수신자 · 템플릿 키 · 변수 · 채널 우선순위 · 멱등 키)
        ▼
D·알림  ┌─ 채널 라우팅 · 폴백 ─────────── 새로 만든다
        ├─ 이메일 엔진   ← 이 저장소에서 떼어온 것
        ├─ SMS 엔진
        └─ 알림톡 엔진
        │  ↑ 발송 결과 회신 (성공 · 실패 · 반송 · 수신거부)
        ▼
     D·감사
```

이메일 엔진이 책임지는 범위는 **"이메일 채널 하나를 안정적으로 밀어내고 결과를 돌려주는 것"**
까지다. 누구에게 무엇을 어느 채널로 보낼지는 위층이 정한다.

## 표준 연동 규격에서 정해야 할 것

엔진을 떼기 전에 위층과 합의가 필요한 항목이다. 내부 구현보다 이쪽이 먼저다.

- **멱등 키** — 같은 이벤트로 두 번 호출돼도 한 번만 나가야 한다. 지금 MCP 설계에 있는
  `(workspace_id, idempotency_key)` 유니크와 같은 방식([mcp-integration-design.md](mcp-integration-design.md)).
- **수신거부·억제의 소유자** — 억제 명단을 알림 컴포넌트가 갖는가, 고객 도메인(B)이 갖는가.
  통지(계약 만료 같은 의무 고지)는 수신거부 대상이 아닐 수 있어 **채널·유형별로 갈린다.**
  이건 법무 판단이 섞이는 지점이다.
- **발송 결과 회신 방식** — 동기 응답으로 접수만 알리고 결과는 콜백/이벤트로 보내는 형태가
  맞다. 반송은 수 시간 뒤에도 온다.
- **템플릿 소유자** — 알림톡은 카카오 사전 승인 템플릿만 쓸 수 있어 이메일의 자유 HTML 과
  모델이 다르다. 채널별로 템플릿 관리 주체가 갈릴 가능성이 높다.
- **재시도·타임아웃 예산** — 위층 폴백과 아래층 재시도가 겹치면 같은 사람에게 두 번 간다.
  누가 몇 번 재시도하는지를 규격에 못 박아야 한다.

## 값어치가 어디 있는가

**코드량이 아니라 사고 이력이다.** 가져갈 12개 남짓은 파일 수로는 적지만, 그 안의 판단은
전부 한 번씩 데인 결과이고 [AUDIT-2026-08-21.md](AUDIT-2026-08-21.md) 의 ARCH-1~12 와
[OPS-LOG.md](OPS-LOG.md) 에 근거가 남아 있다.

| 판단 | 왜 그렇게 됐나 |
| --- | --- |
| stale 재클레임 2분 | SMTP 최악 70초(연결 10 + 읽기 30 + 쓰기 30)에서 역산 — ARCH-4 중복 발송 |
| 종료 기록에 claim 토큰(`updated_at`) | 재클레임·바운스 웹훅과 경합해 결과를 덮어쓰던 문제 — ARCH-4 |
| 억제를 팬아웃에서 미리 거름 | 발송 시점에 빼면 잡·토큰·DB 왕복이 낭비 — ARCH-10 |
| 복구 스위퍼(10분) | claim 에 이긴 뒤 죽으면 DLQ 도 안 가고 영구 고착 — ARCH-1·2·5 |
| A/B 판정에 최소 표본·유예 | 표본 0·동률이 조용히 "A 승"으로 확정되던 문제 — ARCH-6 |
| 워커 종료 예산 > SMTP 최악 | 배포 중 SIGKILL 이 중복 발송으로 이어짐 — 2026-09-23 |

**그래서 "새로 짜는 게 빠르지 않나"의 답은 아니오다.** 새로 짜면 같은 함정을 다시 밟는다.
다만 **통째로 옮기는 것도 아니다** — 위 ①만 들고 나가 새 경계 안에서 재조립하는 형태다.

## 남은 판단거리

- **어느 저장소에 두는가** — 그 플랫폼 저장소 안의 모듈로 넣는가, 별도 저장소로 두고
  서비스로 호출하는가. 4GB 노드 제약이 없는 환경이면 후자가 경계를 지키기 쉽다.
- **[notification-fork-design.md](notification-fork-design.md) 와의 관계** — 독립 SaaS 포크와
  이 컴포넌트 분리를 **둘 다 하면 같은 엔진이 세 벌**(Outpace, 포크, 컴포넌트)이 된다.
  둘 중 하나를 고르거나, 엔진을 공용 라이브러리로 빼는 결정이 선행돼야 한다.
- **착수 시점** — Outpace 자체가 아직 매출 전이다. 어느 쪽이든 그 궤도에 오른 뒤가 맞다.
